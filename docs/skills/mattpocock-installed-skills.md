# 已安装的 Matt Pocock Skills 使用手册

## 这份手册的范围

本机验证到 28 个由 `mattpocock/skills` 安装器锁定的 Skill 副本，均在 `C:\Users\A2134\.agents\skills\<skill-name>\SKILL.md`。锁记录位于 `C:\Users\A2134\.agents\.skill-lock.json`，记录了上游路径、目录内容哈希和安装时间。它们的安装时间集中在 2026-07-17。

这证明的是“本机锁定副本来自这个上游仓库”，不是“本机内容等于 GitHub 当前 HEAD”。锁文件里的 `skillFolderHash` 是目录内容哈希，不是 Git commit SHA。不要把它写成上游版本号，也不要把其他来源的 Skill 算进本清单。

这些 Skill 不是 npm 包、CLI 命令或项目运行时依赖。它们是给 Coding Agent 的工作流说明：任务命中后，Agent 先完整阅读相应 `SKILL.md` 和其要求的引用材料，再按定义的输入、过程、产物和边界执行。Skill 的存在不等于每个任务都要使用它；正确做法是按任务信号主动选择最小且充分的一组。

## 使用机制

### 选择、读取与优先级

1. 先判断任务属于需求澄清、规格、拆票、实现、故障、研究、设计、审查、交接还是写作。
2. 命中本手册中的触发条件后，读取对应 `SKILL.md`；用户点名的 Skill 必须使用。
3. 同时命中多个 Skill 时，按工作流的先后顺序组合，而不是让多个 Skill 重复做同一件事。
4. 优先级始终是：用户的明确要求 > 本仓库 `AGENTS.md` > Skill 规则 > 通用习惯。Skill 不会授权绕开用户确认、凭据保护、代码审查或提交规则。
5. 每个可审计的工程结论都写回本仓库的 `.scratch/` 任务记录；不要只留在聊天上下文。

### 主动调用门槛

每次选中 Skill 后，必须先检查它本机 `SKILL.md` 的 front matter：

- 没有 `disable-model-invocation: true` 时，Agent 可以在任务语义匹配的前提下主动使用。
- 有 `disable-model-invocation: true` 时，该 Skill 只能由用户明确请求。Agent 可以说明“建议使用哪个 Skill、为什么”，但不能因为它匹配路由就自行开始该工作流。

因此，下面的流程图和“何时使用”只描述语义适配性，并不覆盖这个调用门槛。尤其是规划、规格、拆票、实施、triage 和交接类流程常需要用户的显式触发。

### 主工程路径

`模糊想法/需求
  -> grill-with-docs
  -> to-spec
  -> to-tickets
  -> implement + tdd
  -> code-review
  -> 用户确认后提交`

分支路径：

- 外部原始反馈先走 `triage`。
- 难复现故障先走 `diagnosing-bugs`。
- 大型项目且技术路线未定先走 `wayfinder`，消除关键未知后才进入 `to-spec`。
- 依赖事实、官方 API 或规范时先走 `research`。
- 对状态或接口形状无法靠文字决定时，先做窄 `prototype`。

## 工程类 Skills

### `ask-matt`

**何时使用：** 人明确要求“该用哪个 Matt Pocock Skill”或工程流程路线完全不清时。

**机制：** 它是路由入口，会根据“想法到交付”的主线以及故障/大型项目分支指向下一项 Skill，而不是直接产生代码、规格或测试。

**边界：** 此 Skill 需要人工明确调用，不应由 Agent 静默套用。已有清晰 ticket、测试目标或审查基线时，直接进入相应 Skill 更有效。

### `code-review`

**何时使用：** 一个固定基线之后的改动、完成的 ticket、分支或 PR 需要审查时。

**机制：** 将审查拆为两条独立轴：`Standards` 检查仓库书面规范和可维护性坏味道，`Spec` 检查是否忠实实现原始规格。两条轴应由互不污染上下文的审查者独立产出结果，再并列汇总。

**产物与边界：** 每个发现要有严重级别、文件/行定位、影响和复验方式。它不能替代需求澄清、测试或故障定位；在本仓库中发现必须写入对应 issue 的 `Review History`，修复后重新独立审查，直到无未解决问题。

### `codebase-design`

**何时使用：** 模块职责混乱、接口泄漏实现、调用方需要知道过多内部细节、代码难测或一次小改动波及很多地方时。

**机制：** 用“深模块、窄接口、边界、适配器、局部性和杠杆点”检查设计。目标是让一个模块在小接口后吸收更多复杂性，而不是通过更多抽象层掩盖问题。

**边界：** 适合真实的模块形状问题，不适合格式化、机械改名或无证据的大规模重写。设计结论应回流到规格和 ticket，而不是停在观点层面。

### `diagnosing-bugs`

**何时使用：** 间歇性 bug、性能回归、难复现失败、修过又复发的问题。

**机制：** 先建立短而稳定的失败反馈循环；列出并验证假设；找到能解释所有现象的根因；写回归测试；以最小改动修复并复验。

**边界：** 没有明确症状、只是预防性重构或还在讨论产品需求时不适合。不要先猜根因再修改代码，也不要把“测试偶尔通过”当成已定位。

### `domain-modeling`

**何时使用：** 同一个业务词被不同人用于不同意思、实体/状态关系说不清，或出现值得长期记录的领域决策时。

**机制：** 用 `CONTEXT.md` 维护精炼的项目词汇表，明确首选术语与应避免的同义词；遇到真正难逆、意外且有取舍的决定时，才创建 ADR。

**边界：** `CONTEXT.md` 只写领域语言，不写 TypeScript、脚本、超时或实现细节。当前仓库没有已解析的领域词时，不要为了凑初始化而创建空文件或空 ADR。

### `grill-with-docs`

**何时使用：** 仓库内的功能想法、产品要求或技术决策仍含糊，且澄清结果应该成为长期项目上下文时。

**机制：** 使用深入追问把“可以由 Agent 查证的事实”和“必须由用户作出的取舍”分开；将已经稳定的结论沉淀到领域文档、ADR 或规格中。

**边界：** 已经具备明确范围、验收条件和边界的 issue 不需要重新访谈。它的价值是减少错误假设，不是无限延长讨论。

### `implement`

**何时使用：** 已有可独立验证、范围明确的规格或 ticket，需要实施时。

**机制：** 以 ticket 为边界推进；尽可能配合 `tdd`；持续运行类型检查和局部测试；完成后转入 `code-review`。

**边界：** 不能替代规格和拆票。Skill 中的提交流程受本仓库规则约束：审查无问题后仍必须先征得用户批准，才可提交。

### `improve-codebase-architecture`

**何时使用：** 有专门的非功能维护时间，想系统发现可维护性、模块边界、重复或耦合问题时。

**机制：** 扫描架构机会，挑出有证据的候选项，并把它们重新放入澄清、规格和 ticket 流程。

**边界：** 它不是“大重写许可证”。没有验收标准、风险控制和可验证收益的重构不应启动。

### `prototype`

**何时使用：** 通过文字无法判断状态机、交互手感、业务流程、解析规则或 API 形状是否可行时。

**机制：** 建立一个窄、可运行、专门用来证伪或验证假设的原型；把原型证明的结论而不是整段试验代码带回规格。

**边界：** 原型必须和生产实现区分，不可因为“能跑”就直接作为正式架构。只有不确定性真实存在时才值得创建。

### `research`

**何时使用：** 依赖官方文档、标准、API、工具版本、兼容性、供应商行为或其他一手证据来做决定时。

**机制：** 优先研究一手来源，产出带来源引用的 Markdown 结论，让规格或设计能引用已核验的事实。库、框架、SDK、API、CLI 或云服务必须先取当前 Context7 文档。

**边界：** 研究不能替用户做产品取舍，也不能用未核验的搜索摘要代替来源。结论过期风险高时要注明核验日期。

### `resolving-merge-conflicts`

**何时使用：** 当前确实处于 Git merge 或 rebase 冲突状态。

**机制：** 对每个冲突 hunk 追溯双方的意图和一手来源，按意图而非“左边/右边谁新”进行合并，测试后继续合并或变基。

**边界：** 不用于假想比较或普通设计讨论。除非用户明确要求，不要通过 `--abort` 丢弃进行中的冲突工作。

### `setup-matt-pocock-skills`

**何时使用：** 第一次为某个仓库安装这套工程工作流，或确实需要切换 issue tracker、triage 词汇、领域文档布局时。

**机制：** 检查现有远程、任务追踪、领域文档、单/多上下文线索，建立后续 Skill 需要读取的仓库约定。

**边界：** 不能覆盖已有约定。本仓库已经使用本地 `.scratch/` tracker，因此应保留它；没有已解决术语时不提前生成 `CONTEXT.md` 和 `docs/adr/`。

### `tdd`

**何时使用：** 能先写出一个可观察、可验收的外部行为时。

**机制：** 红：写出会失败的行为测试；绿：实现刚好足以通过的最小代码；重构：在保持测试绿的前提下改善结构。

**边界：** 需求仍模糊、没有可靠行为断言或只是配置/文档变更时不能硬套。测试应验证外部行为，不应绑定内部实现细节。

### `to-spec`

**何时使用：** 当前讨论已经收敛，需要让需求可实施、可审查、可验证时。

**机制：** 将问题、解决方案、用户故事、实现决定、测试决定、非目标和补充说明固化为规格，避免实现时重新猜测范围。

**边界：** 重大产品选择尚未解决时先 `grill-with-docs`。本仓库的本地 issue-tracker 格式优先于 Skill 的通用示例格式。

### `to-tickets`

**何时使用：** 规格已准备好，需要并行、多会话或可独立验证的执行单元时。

**机制：** 拆成 tracer-bullet 的纵向 ticket；每个 ticket 都明确它交付的用户可验证行为、验收条件和真实的 blocking edges。

**边界：** 单会话能完成的很小改动不需要人为切碎。本仓库把本地 ticket 放在 `.scratch/<feature>/issues/`，并遵守 `docs/agents/issue-tracker.md` 的状态和审查记录规范。

### `triage`

**何时使用：** 外部提交的原始 bug、意见、需求或报告信息不完整，需要判断类别、优先级、复现性和下一步时。

**机制：** 将原始输入梳理为可实施的 agent-ready issue，必要时标记缺信息或不修复。

**边界：** 已经由 `to-tickets` 创建、范围和验收齐全的 ticket 不要再 triage。使用 `docs/agents/triage-labels.md` 中的本地标签词汇。

### `wayfinder`

**何时使用：** 绿色项目、大功能或复杂改造的目的明确，但路线、技术选择或风险点仍有大量未知时。

**机制：** 先建立由“决策 ticket”组成的路线图，逐个消除最高风险未知；当路线足够清楚时再生成正式规格。

**边界：** 对明确的小功能来说过重。它不是直接开工的替代品，也不应把探索性结论当作已经批准的实现。

## 生产力类 Skills

### `grill-me`

**何时使用：** 没有仓库上下文，但希望严谨挑战一个计划、决策、写作方向或个人目标时。

**机制：** 多轮追问，迫使假设、证据、约束和取舍变得明确。

**边界：** 在项目中需要留下长期记录时优先 `grill-with-docs`；它本身不会创建仓库规格或代码。

### `grilling`

**何时使用：** 只需要“深度追问、缩小决策前沿”这一基本能力时。

**机制：** 将未知区分为可由 Agent 查证的事实与只能由用户决定的选项，逐轮收敛。

**边界：** 只负责澄清，不能代替 `to-spec`、`to-tickets` 或实现。

### `handoff`

**何时使用：** 会话、人员、工作树或责任确实发生边界切换时。

**机制：** 生成可移交的 Markdown，覆盖当前状态、证据、改动、风险、未决问题和下一行动。

**边界：** 不要把每条回复都伪装成交接，也不要把它当作无意义的上下文压缩工具。

### `teach`

**何时使用：** 用户要在多轮中学习一个概念、练习技能并持续保留学习状态时。

**机制：** 将工作目录作为学习空间，按已有理解安排练习、检验和复盘。

**边界：** 不替代生产代码实施、审查或正式规格流程。

### `writing-great-skills`（遗留，仅显式调用）

**何时使用：** 设计、创建或改进一个给 Coding Agent 使用的 Skill 时。

**机制：** 规定准确触发描述、前置条件、分步工作流、产物契约、工具边界和渐进披露，避免把 Skill 写成难执行的口号。

**边界：** 该本地副本已被上游替换，不能作为默认路由。只有用户明确要求时才使用，并人工复核结果；普通 README、业务文档或代码注释不应为了使用这个 Skill 而过度流程化。

## 个人类 Skills（遗留，仅显式调用）

### `obsidian-vault`（遗留，仅显式调用）

**何时使用：** 用户确实要搜索、创建或整理 Obsidian vault 中的笔记。

**机制：** 遵守 vault 的 wikilink、索引和组织方式，保持知识图谱可导航。

**边界：** 该本地副本已不在上游仓库中，而且硬编码了 Linux vault 路径。不要默认使用；用户必须显式授权并先提供或确认实际的 Windows vault 路径。普通仓库 Markdown 不等于 Obsidian 笔记；不要把项目文档强行搬进 vault。

### `edit-article`（遗留，仅显式调用）

**何时使用：** 有一篇既有文章需要改善结构、表达、清晰度和一致性时。

**机制：** 从文章目标和读者出发做针对性编辑，保留原文意图。

**边界：** 该本地副本已不在上游仓库中，不能作为默认路由。只有用户明确要求编辑文章时才使用；技术事实仍应由 `research` 或官方文档核验，文章润色不等于事实审查。

## 限制状态的 Skills

### `request-refactor-plan`（已废弃）

**原机制：** 通过访谈产生小步重构计划，并把它作为 GitHub issue 发布。

**当前用法：** 默认不要使用。对于本地 tracker，优先 `grill-with-docs -> to-spec -> to-tickets`；只有用户明确要求旧流程时才启用。

### `design-an-interface`（已废弃）

**原机制：** 并行生成明显不同的 API、UI 或模块接口候选，再比较取舍。

**当前用法：** 默认不要使用。只在真实存在接口设计难题且用户明确要求多方案比较时，才考虑它或使用当前替代流程。

### `writing-fragments`（开发中）

**何时使用：** 探索短文、片段或未定稿写作时。

**边界：** 这是实验性流程，不能未经人工复核就用于正式规格、工程决策或用户承诺。

### `writing-shape`（开发中）

**何时使用：** 需要探索写作结构、段落组织和表达节奏时。

**边界：** 同样只适合低风险试用；正式项目文档仍需按事实、规格和审查流程验证。

## 当前 `ytops` 项目的推荐组合

| 场景                                             | 推荐组合                                                                     |
| ------------------------------------------------ | ---------------------------------------------------------------------------- |
| 用户提出一个新的 CLI 行为，但目标仍含糊          | `grill-with-docs -> to-spec -> to-tickets -> implement + tdd -> code-review` |
| 用户报告下载、授权、URL 校验或 JSON 输出回归     | `diagnosing-bugs -> tdd -> implement -> code-review`                         |
| 要接入外部 API、MCP、OAuth、yt-dlp 或新的 npm 包 | `research`（先查当前官方文档）-> `grill-with-docs`（如有选择）-> `to-spec`   |
| 发现 CLI 和项目 Skill 的职责边界漏水             | `codebase-design`，必要时补 `domain-modeling`                                |
| 要变更本地 task tracker 或由本地转 GitHub        | `setup-matt-pocock-skills -> triage`，并经用户确认后才写入新约定             |
| 当前改动准备交付                                 | `code-review`；无未解决问题后请求用户批准提交                                |

## 不是本清单的 Skills

下列可用 Skill 并非来自 `mattpocock/skills`，不能写进“Matt Pocock 已安装清单”：`hallmark`、`humanizer`、`orchestration`、`computer-use`、`orca-cli`、`hyperframes` 系列和 `media-use`。它们仍可能在各自任务中有价值，但应按自己的来源和规则使用。
